## 附录第 2 页：一段会话，两层循环

### 本页目标

解释为什么已经存在一个 `while (true)`，生产级系统仍然要拆分为外层 `QueryEngine` 和内层 `queryLoop`。

关键不是多套一层相同的循环，而是分开两种时间尺度：

- 外层管理一整段会话；
- 内层完成当前这一次用户请求。

人物：若叶墨，努力思考的表情。

### 区块 2：一段会话包含多次任务

外层标题：**`QueryEngine`：管理整段会话**

外层覆盖从打开会话到离开的整个生命周期，负责：

- 恢复已有会话；
- 等待和接收多次用户输入；
- 累计 Token 与费用；
- 保存会话状态。

结构图：

```text
QueryEngine：整段会话
│
├─ 用户第 1 次输入：“读取文件”
│  └─ queryLoop #1
│     调用模型 → 执行工具 → 送回结果
│          ↑                     │
│          └──── 可能重复多轮 ───┘
│     无工具调用 → 返回最终回答
│
└─ 用户第 2 次输入：“继续修改”
   └─ queryLoop #2
      调用模型 → 搜索或编辑 → 验证结果
           ↑                         │
           └──── 可能重复多轮 ───────┘
      当前任务完成 → 返回外层
```

### 区块 3：两层分别关心什么

左侧标题：**外层问：“整段会话还好吗？”**

- 用户下一句话什么时候到来？
- 会话是否需要从磁盘恢复？
- 总预算和 Token 已经使用多少？
- 当前状态什么时候保存？

右侧标题：**内层问：“这次任务怎样做完？”**

- 这一轮是否需要调用工具？
- 工具结果怎样送回模型？
- 当前执行遇到可恢复错误时怎么办？
- 什么时候产生最终回答并返回外层？

### 区块 4：祥子解释关注点分离

人物：丰川祥子，认真讲解。

### 本页结论

> `QueryEngine` 管“一段关系”，`queryLoop` 管“一次任务”。

## 附录第 3 页：两端握手，一次一步

### 本页目标

解释 `yield` 与 `for await...of` 的区别，以及为什么背压来自生产端与消费端的配合，而不是由某一个关键字单独提供。

关键边界：

- `yield` 是生产端语法，负责交出一个值并暂停生成器；
- `for await...of` 是消费端语法，负责等待一个值、处理它，然后再请求下一项；
- 普通 `for` 循环中的 `await` 通常只控制已有数据的处理顺序，并不控制数据怎样产生。

### 区块 1：墨提出问题

人物：若叶墨，认真提问。

墨：

> “`yield` 会暂停，`for await` 也会等待……”
>
> “它们是同一种写法吗？到底是谁在等谁？”

### 区块 2：异步迭代协议的两端

左侧标题：**生产端：`async function*`**

- `yield event` 把一个事件交给消费者；
- 交出事件后，生成器暂停在当前位置；
- 直到消费者再次请求下一项，生成器才从上一个 `yield` 后继续运行。

右侧标题：**消费端：`for await...of`**

- 等待异步迭代器产生一个结果；
- 取得事件后执行当前循环体；
- 当前循环体没有完成，就不会主动请求下一项。

中间使用编号流程：

```text
1. for await 调用 iterator.next()
                     ↓
2. 生成器继续运行到下一次 yield
                     ↓
3. yield 交出事件，同时暂停生产端
                     ↓
4. 消费端执行并等待 render(event)
                     ↓
5. 循环体结束，再次请求 iterator.next()
```

### 区块 3：生产端与消费端代码

生产端：

```ts
async function* queryLoop() {
  yield textEvent;
  yield toolEvent;
  yield finalEvent;
}
```

消费端：

```ts
for await (const event of queryLoop()) {
  await render(event);
  // render 完成后，循环才取得下一项
}
```

### 区块 4：`for await...of` 隐藏的迭代过程

使用近似展开代码解释 `for await...of`：

```ts
const iterator = queryLoop();

while (true) {
  const { value, done } = await iterator.next();
  if (done) break;

  await render(value);
}
```

说明：消费端反复调用异步迭代器的 `next()`，等待结果，再运行循环体；只有循环体完成后才开始下一轮。

### 区块 5：与普通 `for + await` 对比

普通串行处理：

```ts
for (const event of existingEvents) {
  await handle(event);
}
```

这里的 `existingEvents` 通常已经全部存在。`await` 保证处理过程按顺序完成，但没有反向限制这些数据怎样产生。

异步按需生产：

```ts
for await (const event of asyncSource) {
  await handle(event);
}
```

每一项由异步生产者按需产生。消费者不请求下一次 `next()`，按需推进的生产者就不会继续越过当前的 `yield`。

### 区块 6：美奈美的类比与祥子的修正

人物：森美奈美，端着点心；丰川祥子，准确补充。

美奈美：

> “妈妈交出一盘，墨墨接稳以后才交下一盘。”

祥子：

> “一边负责交，一边负责再要。”
>
> “两者配合，才形成背压。”

### 本页结论

> 背压不是 `yield` 单独提供的。它来自“生产端可以暂停”与“消费端按需请求下一项”的握手。

### 准确性补充

本页描述的是按需推进的异步生成器模型。如果生产者另行启动后台任务并主动缓存大量事件，仍然可能产生积压；`yield` 本身不会自动限制这些额外的后台生产。

## 附录第 4 页：不是只有一种 `continue`

### 本页目标

建立生产级循环七种继续原因的全局地图。

关键认知：`continue` 只是相同的控制流动作，不代表相同原因。不同原因需要在下一轮开始前执行不同准备工作。

### 区块 1：墨提出疑问

人物：若叶墨，疑惑表情。

墨：

> “模型没有再调用工具，不就应该结束了吗？”
>
> “为什么生产级循环还会有七种‘继续’？”

### 区块 2：最小版与生产级判断对照

最小版只判断工具调用：

```ts
if (toolUses.length > 0) {
  continue;
}

break;
```

生产级循环需要先判断当前查询是否真正终结：

```ts
const decision = inspectOutcome(response);

if (decision.kind === "done") break;

prepareNextAttempt(decision.reason);
continue;
```

这段代码是用于表达设计的伪代码，不表示参考实现中的真实接口。

### 区块 3：七种原因分为四组

#### 第一组：正常行动

`next_turn`

- 模型调用了一个或多个工具；
- 运行时执行工具并把结果送回消息数组；
- Agent 根据结果继续下一轮。

#### 第二组：上下文恢复

`collapse_drain_retry`

- API 报告上下文过长；
- 系统存在已识别、但尚未应用的折叠操作；
- 先应用这些折叠以腾出空间，然后重试。

`reactive_compact_retry`

- 应用轻量折叠以后，上下文仍然过长；
- 系统启动更重的全量摘要压缩；
- 使用压缩后的上下文再次尝试。

#### 第三组：输出恢复

`max_output_tokens_escalate`

- 模型的回答第一次被输出上限截断；
- 系统提高允许的输出上限；
- 重新尝试生成。

`max_output_tokens_recovery`

- 提高上限后仍然没有完整输出；
- 系统注入续写提示；
- 在有限次数内继续生成，避免无限循环。

#### 第四组：系统要求继续

`stop_hook_blocking`

- 模型本轮已经没有 `tool_use`，按最小循环本应结束；
- 运行时在真正结束前执行 Stop Hook；
- Stop Hook 返回 `block` 和尚未满足的原因；
- 运行时把原因送回下一轮，让 Agent 继续工作；
- Hook 返回允许停止以后，循环才真正结束。

`token_budget_continuation`

- 单次生成可使用的 Token 预算已经耗尽；
- 当前回答或任务仍未完整结束；
- 系统继续请求后续生成，而不是把一次预算耗尽误判为任务完成。

### 区块 4：是谁要求继续

用三个并列框说明：

1. **模型要求继续**：模型需要调用工具取得信息或执行行动；
2. **运行时要求继续**：当前响应遇到可以恢复的上下文或输出问题；
3. **系统策略要求继续**：验收条件尚未成立，或者一次生成只是暂时用完预算。

### 区块 5：祥子解释“原因”为什么重要

人物：丰川祥子，严谨说明。

祥子：

> “`continue` 只是相同的控制流动作，却不是相同的原因。”
>
> “调用工具以前要执行工具；上下文太长以前要先压缩；输出被截断以前要先扩容或者续写。”
>
> “如果不知道为什么继续，就无法正确准备下一轮。”

### 本页结论

> 生产级循环判断的不只是“有没有 `tool_use`”，而是“当前查询是否已经进入不可再继续的终态”。

本页采用 `.references/cc-from-scratch/01-agent-loop.md` 中的七种原因命名，用于说明该参考资料对生产级循环的拆解。页面先建立分类地图，后续再解释恢复过程，不在本页声称这些名称是稳定的公共 API。

## 附录第 5 页：系统记得，不等于模型看见

### 本页目标

解释系统内部保存的完整会话历史，与本轮真正发送给模型的 `messages` 可以不是同一份内容。

关键认知：

- 完整历史是系统内部保存的事实来源；
- 本轮发送给模型的消息由完整历史派生；
- 模型只能看见当前请求实际包含的内容；
- 折叠本轮请求中的旧内容，不等于永久删除完整历史。

本页首次出现“请求视图”时，必须先使用完整名称“本轮发送给模型的 `messages`”，不能直接假设读者理解“API 视图”。

### 区块 1：墨提出疑问

人物：若叶墨，新的疑问。

墨：

> “消息不是一直放在 `messages` 里吗？”
>
> “系统保存了完整历史，模型不就也能全部看见吗？”

### 区块 2：从完整历史构造本轮请求

使用三段管道图：

```text
完整会话历史
      ↓
构造本轮请求
      ↓
真正发送给模型的 messages
```

三段分别说明：

1. **完整会话历史**：系统内部保存的用户消息、模型回答、工具调用与完整结果；
2. **构造本轮请求**：规范化协议结构、保持工具配对、折叠旧内容、选择最近和关键消息；
3. **本轮请求消息**：模型这一轮实际能够读取的上下文。

用教学伪代码表示：

```ts
const fullHistory = loadCompleteHistory();
const messagesForAPI = buildMessagesForAPI(fullHistory);

await client.messages.create({
  messages: messagesForAPI
});
```

`fullHistory` 与 `messagesForAPI` 都是用于解释概念的名称，不表示参考实现中的真实接口。

### 区块 3：同一段会话的两种形态

左侧标题：**系统内部：完整历史**

```text
user：帮我修复问题
assistant：tool_use(read_file, id=01)
tool_result(id=01)：两万字文件内容……
assistant：tool_use(grep_search, id=02)
tool_result(id=02)：一万字搜索结果……
最近的重要对话……
```

右侧标题：**当前请求：派生消息**

```text
user：帮我修复问题
assistant：tool_use(read_file, id=01)
tool_result(id=01)：[旧结果已折叠，需要时重新读取]
assistant：tool_use(grep_search, id=02)
tool_result(id=02)：[旧搜索结果已折叠]
最近的重要对话保持完整……
```

右侧必须保留两个准确性提示：

- 工具结果内容可以缩短，但 `tool_use` 与对应 `tool_result` 的顺序和 ID 配对仍须合法；
- 完整内容仍保存在系统内部，需要时可以重新读取或重新构造请求。

### 区块 4：什么是“已识别、但尚未应用”的折叠操作

使用三个阶段解释：

#### 1. 找出候选内容

系统判断旧文件结果、旧搜索结果等内容可以在后续请求中缩小。

教学伪代码：

```ts
pendingCollapses = [
  fold(oldReadResult),
  fold(oldSearchResult)
];
```

#### 2. 折叠操作暂存，尚未应用

系统已经识别出“哪些旧内容可以折叠”，并暂存了对应操作；但这些操作尚未应用，也没有修改下一次发送给模型的 `messages`。

#### 3. Drain 并重建请求

API 报告上下文过长以后，系统取出并应用这些暂存的折叠操作，重新构造较小的请求，然后再次调用模型。

这里的 `drain` 指：

> 把等待队列中的折叠操作全部取出并应用。

它不表示排空消息历史，也不表示删除整段对话。

> 完整历史是系统的事实来源；本轮发送给模型的 `messages` 是由它派生出来的请求内容。

### 前端开发者类比

- 完整历史类似 Store 中的源状态；
- 本轮请求类似从源状态派生出的 computed 结果；
- 类比用于理解数据边界，不代表真实源码接口。

### 诚实边界

参考文档说明存在已识别但尚未应用的折叠操作，并在上下文过长后提交；但没有在第一章公开具体识别时机或队列数据结构。`pendingCollapses`、`fullHistory` 和 `messagesForAPI` 都是教学伪代码，不能作为真实实现名称引用。

- 不解释折叠候选内容的完整选择算法；
- 不讨论前缀缓存与折叠之间的关系；
- 不展开全量摘要压缩；
- 不说明上下文管理的完整五级流水线。

### 与下一页的衔接

## 附录第 6 页：先用轻的，再用重的

### 本页目标

解释上下文过长以后，为什么生产级循环先执行 `collapse_drain_retry`，仍然无法恢复时才升级为 `reactive_compact_retry`。

关键认知：两级恢复不是重复工作，而是渐进式升级。更重的恢复通常更贵、更慢、信息损失更多，因此系统先尝试能够解决问题的最轻手段。

### 区块 1：墨继续追问

人物：若叶墨，追问表情。

墨：

> “既然全量摘要肯定能缩小上下文……”
>
> “为什么不在第一次报错时就直接总结？”

### 区块 2：上下文过长错误

终端显示：

```text
prompt too long
```

解释：本轮准备发送给模型的 `messages` 超过上下文窗口，请求无法正常继续。

不要把它与“模型输出被截断”混为一谈：这里出问题的是输入给模型的上下文，而不是模型正在生成的回答。

### 区块 3：两级恢复阶梯

```text
API 返回 prompt too long
          ↓
是否存在已识别、但尚未应用的折叠操作？
    ├─ 有 → 应用折叠并重建较小的 messages
    │          ↓
    │       重新请求
    │      ├─ 成功 → 正常继续
    │      └─ 仍然太长 → 升级为全量摘要
    │
    └─ 没有 → 直接升级为全量摘要
               ↓
          使用摘要与最近消息构造新上下文
               ↓
             重新请求
```

### 区块 4：轻恢复——`collapse_drain_retry`

- 取出并应用已识别、但尚未应用的折叠操作；
- 把折叠结果用于下一次模型请求；
- 不需要额外调用模型生成整段历史摘要；
- 主要缩小本轮请求内容；
- 通常速度更快，信息损失较少。

### 区块 5：重恢复——`reactive_compact_retry`

- `reactive` 表示在实际收到 `prompt too long` 后被动触发；
- 系统调用模型或相应摘要机制，压缩较早的会话历史；
- 后续请求使用摘要与最近消息构造较小的上下文；
- 成本和延迟更高；
- 摘要属于有损压缩，可能遗漏原始细节。

### 区块 6：为什么按这个顺序

使用三个并列理由框：

1. **更便宜**：已有折叠能够解决时，不额外调用模型制作摘要；
2. **更快**：应用已有变更通常比重新生成整段对话摘要更快；
3. **更少损失**：摘要是有损压缩，越晚使用，越能保留原始细节。

### 区块 7：教学伪代码

```ts
try {
  return await callModel(messagesForAPI);
} catch (error) {
  if (!isPromptTooLong(error)) throw error;

  if (hasPendingCollapse()) {
    drainPendingCollapses();
    continue; // collapse_drain_retry
  }

  await compactConversation();
  continue; // reactive_compact_retry
}
```

这段代码只表达恢复顺序。`hasPendingCollapse`、`drainPendingCollapses` 与 `compactConversation` 不表示参考实现公开的真实函数签名。

### 区块 8：祥子与睦总结

人物：丰川祥子，严谨说明；若叶睦，安静总结。

祥子：

> “恢复策略应当从代价最小的手段开始。”
>
> “若轻量投影已经足够，就没有理由先支付摘要的成本，并承担额外的信息损失。”

睦：

> “能只收起一部分，就不要先重写整段记忆。”

### 本页结论

> 两级恢复是一道逐级升级的阶梯：先尝试最便宜、最少损失的办法，失败后才使用更重的恢复。

## 附录第 7 页：装不下，还是说不完？

### 本页目标

区分“输入上下文过长”和“模型输出被截断”，并解释生产级循环如何用 `max_output_tokens_escalate` 与 `max_output_tokens_recovery` 两级策略恢复未完成的输出。

关键认知：两种问题都与 token 上限有关，但发生在不同方向，恢复方法也不同。

### 区块 1：墨把两个问题混在了一起

人物：若叶墨，抱着小白困惑地比较两条错误信息。

墨：

> “输入太长和输出太长……不都是 token 不够吗？”
>
> “把上限调大不就好了吗？”

### 区块 2：先看发生在哪一边

使用左右对照卡片：

| 情况 | 发生时机 | 真正含义 | 恢复方向 |
| --- | --- | --- | --- |
| 输入上下文过长 | 模型开始回答之前 | 本轮请求装不进上下文窗口 | 缩小发送给模型的 `messages` |
| 输出达到 `max_tokens` | 模型生成回答期间 | 本次允许生成的额度已经用完，回答可能尚未结束 | 提高输出上限，或让模型继续说完 |

睦：

> “输入过长，是你交给我的东西装不下。”
>
> “输出被截断，是我还没说完，却用完了这一次允许说的话。”

### 区块 3：输出恢复的第一级——提高上限

第一次收到 `max_tokens` 时，循环提高下一次请求允许的最大输出量，再重新尝试。

```text
普通输出额度：16K
        ↓ 首次达到上限
提高输出额度：64K
        ↓
重新请求
```

这对应参考实现中的：

```text
max_output_tokens_escalate
```

这里的 `16K → 64K` 是参考实现给出的策略示例，不是所有模型和 API 都必须采用的固定数值。

### 区块 4：输出恢复的第二级——请求续写

如果已经使用更高上限，回答仍因 `max_tokens` 被截断，继续无限提高上限并不可靠。循环改为追加续写提示，让模型从已有结果继续完成剩余内容。

```text
高输出额度仍然被截断
          ↓
加入“从中断处继续完成”的提示
          ↓
再次调用模型
          ↓
成功完成 / 达到最大续写次数
```

这对应：

```text
max_output_tokens_recovery
```

参考实现为续写设置有限次数，避免模型反复被截断时形成无限循环。

### 区块 5：教学伪代码

```ts
if (response.stopReason === "max_tokens") {
  if (!outputLimitEscalated) {
    maxTokens = higherLimit;
    outputLimitEscalated = true;
    continue; // max_output_tokens_escalate
  }

  if (continuationCount < MAX_CONTINUATIONS) {
    appendContinuationPrompt();
    continuationCount++;
    continue; // max_output_tokens_recovery
  }

  throw new OutputStillIncompleteError();
}
```

这段代码只用于表达两级恢复顺序，不表示参考实现公开的真实函数与字段名称。

### 区块 6：为什么不一开始就把输出额度设到最大

使用三个并列理由框：

1. **控制资源预算**：多数回答不需要极高输出额度；
2. **异常更容易收敛**：有上限和次数限制，才不会无限续写；
3. **保留升级空间**：正常请求保持轻量，只有真正需要时才进入恢复路径。

### 本页结论

> 输入过长要缩小上下文；输出被截断要提高输出额度或请求续写。先判断是哪一边达到上限，才能选择正确的恢复策略。

### 诚实边界

- `max_tokens` 是 API 返回的停止原因之一，表示本次生成达到请求允许的输出上限；
- `max_output_tokens_escalate` 与 `max_output_tokens_recovery` 是参考实现对两种恢复分支的命名；
- `16K → 64K` 是参考实现中的示例策略，不应被描述为通用 API 标准。

### 本页不展开

- 不讨论不同模型的上下文窗口与最大输出上限；
- 不解释续写提示如何避免内容重复；
- 不处理流式输出中半截工具调用的恢复；
- 不把本页的输出恢复与 `token_budget_continuation` 混为一谈。

### 与下一页的衔接

## 附录第 8 页：一样是继续，为什么停下？

### 本页目标

区分 API 返回的 `stop_reason` 与 Agent 运行时记录的 continuation reason，避免把 `max_tokens`、`pause_turn` 和 `token_budget_continuation` 当成同一层的概念。

关键认知：`stop_reason` 回答“本次 API 响应为什么停止生成”；continuation reason 回答“Agent 运行时为什么决定再执行一轮”。

### 区块 1：墨看到成功响应

人物：若叶墨，看着终端中的成功状态。

墨：

> “API 都成功返回了，那这项任务应该已经做完了吧？”

### 区块 2：成功响应不等于完整任务结束

```text
HTTP 200 / 得到有效响应
             ≠
整个 Agent 任务已经完成
```

`stop_reason` 是成功响应中的元数据。它表示模型为何停止本次生成，而不是简单宣布整个 Agent 工作已经结束。

响应可能在以下时刻返回：

- 模型自然完成回答；
- 模型请求调用客户端工具；
- 模型达到本次输出上限；
- 服务端工具循环暂时停顿；
- 其他需要运行时继续检查或处理的状态。

### 区块 3：第一层——API 为什么停止生成

本页重点比较两个公开停止原因。

#### `max_tokens`

- 模型达到请求指定的 `max_tokens` 输出上限；
- 响应内容仍然有效，但可能不完整；
- 调用方可以提高输出上限，或根据已有内容请求续写。

#### `pause_turn`

- 服务端工具的采样循环达到单次请求的迭代上限；
- 它不是“输出太长”的另一种写法；
- 调用方应把这次 assistant 的响应内容放回消息历史，并在保留相同工具配置的情况下继续。

### 区块 4：第二层——Agent 为什么再执行一轮

运行时读取 API 的事实，然后选择对应的控制策略。

```text
API 事实：max_tokens
        ↓
运行时选择：max_output_tokens_escalate
         或 max_output_tokens_recovery
```

上层 API 原因和下层运行时策略职责不同，因此名称不必相同，也不应直接混成一张枚举表。

### 区块 5：`token_budget_continuation` 的诚实边界

参考文档还列出：

```text
token_budget_continuation
触发：API 侧 Token 预算耗尽
动作：继续生成
```

但现有参考资料没有给出它对应的公开 API 字段、原始响应结构或完整判定逻辑。

因此附录只能把它描述为：

> 参考项目内部使用的续跑分类；公开 API 中尚未找到可以确认的一一对应项。

不要把它写成 `pause_turn` 的别名，也不要把当前公开的其他预算功能强行套用到这个名称上。

### 区块 6：教学伪代码

```ts
const response = await callModel();

switch (response.stop_reason) {
  case "tool_use":
    return executeToolsAndContinue(response);

  case "max_tokens":
    return recoverTruncatedOutput(response);

  case "pause_turn":
    return resumeServerToolTurn(response.content);

  case "end_turn":
    return checkStopHookBeforeFinishing(response);
}
```

这段伪代码只展示公开停止原因如何进入运行时决策。`token_budget_continuation` 不应在映射尚未得到确认时被伪装成某个公开字段。

### 区块 7：祥子总结两套词

人物：丰川祥子，严谨校对。

祥子：

> “`stop_reason` 回答的是，这次 API 响应为何停在这里。”
>
> “运行时的 continuation reason 回答的是，Agent 为何决定再执行一轮。二者职责不同。”

### 本页结论

> API 响应结束，只代表本次生成停了下来；是否完成整个 Agent 任务，仍要由运行时根据停止原因与控制策略判断。

### 诚实边界

- `max_tokens` 与 `pause_turn` 是 Anthropic Messages API 的公开 `stop_reason`；
- `pause_turn` 用于服务端工具循环达到单次请求的迭代上限，不表示输出达到 `max_tokens`；
- `token_budget_continuation` 来自参考项目的内部分类，现有资料不足以确认它与某个公开停止原因的一一映射；
- 页面中的运行时函数名均为教学伪代码。

- 不列举全部公开 `stop_reason`；

## 附录第 9 页：模型说完了，还不能走？

### 本页目标

解释 Stop Hook 如何把“模型本轮准备结束”变成“等待运行时验收的候选终态”，以及 `stop_hook_blocking` 为什么会让 Agent 带着未满足原因重新进入循环。

关键认知：没有 `tool_use`、模型返回 `end_turn`，只说明本次生成准备结束；配置了 Stop Hook 时，任务还要经过运行时的结束前验收。

### 区块 1：墨以为已经结束

人物：若叶墨，看着终端中的 `end_turn`。

墨：

> “没有工具要调用，模型也说做完了。”
>
> “这次总能直接结束了吧？”

祥子：

> “自称完成，不等于通过验收。”

### 区块 2：从候选结束到真正结束

使用主流程图：

```text
模型完成本次响应
没有工具或其他续跑原因
          ↓
     候选结束状态
          ↓
运行时触发已配置的 Stop Hook
      ├─ 允许停止 → done
      └─ block + reason
                ↓
       把 reason 反馈给模型
                ↓
       stop_hook_blocking
                ↓
         回到循环继续工作
```

Stop Hook 在主 Agent 完成这一轮最终响应、准备停止时触发，并不是只有任务真的完成时才触发。它不在用户主动中断时运行；API 错误会触发没有决策控制的 `StopFailure` 事件，而不是进入 Stop 验收路径。

### 区块 3：Hook 到底是谁执行的

运行时负责在生命周期节点调用 Hook；验收逻辑可以有不同实现。

#### 确定性检查

- 命令、HTTP 或其他程序化 Hook；
- 检查测试退出码、构建产物、文件是否存在、格式是否合规；
- 适合规则明确、可以机械判断的条件。

#### 需要判断的检查

- prompt 型 Hook 可以让独立模型回答条件是否满足；
- agent 型 Hook 可以读取文件、搜索代码或运行工具后再判断；
- 适合“所有需求是否完成”这类需要理解上下文的条件。

所以“Stop Hook 是程序做的还是 LLM 做的”没有唯一答案：**程序负责触发和执行决策；具体检查既可以完全确定性，也可以委托给模型或子 Agent。**

### 区块 4：允许与阻止

#### 允许停止

- Hook 成功且没有返回阻止决定；
- 运行时接受候选终态；
- 当前 Agent 查询真正进入 `done`。

#### 阻止停止

结构化输出可以表示为：

```json
{
  "decision": "block",
  "reason": "测试仍然失败，请先修复再结束"
}
```

`reason` 不是只展示给用户的报错；它会告诉模型为什么不能停止，成为下一轮继续工作的反馈。命令型 Hook 也可以用阻止退出码与错误输出表达同样含义。

### 区块 5：防止 Stop Hook 变成死循环

如果 Hook 永远返回 `block`，Agent 就可能反复尝试结束又被拉回。因此生产实现需要边界：

1. Hook 可以读取 `stop_hook_active`，知道当前响应是否已经由 Stop Hook 续跑产生；
2. Hook 可以检查会话记录，判断是否真的有新进展；
3. 运行时对连续阻止设有上限，达到边界后不再无限续跑；
4. 不可能满足的验收条件应当转成明确失败或请求用户处理，而不是永久空转。

具体阻止上限属于产品策略，不应被描述为 Agent Loop 的固定通用常量。

### 区块 6：教学伪代码

```ts
if (decision.kind === "candidate_stop") {
  const verdict = await runConfiguredStopHooks(state);

  if (verdict.decision === "block") {
    appendFeedback(verdict.reason);
    continue; // stop_hook_blocking
  }

  return; // done
}
```

`candidate_stop`、`runConfiguredStopHooks` 与 `appendFeedback` 都是教学名称，不表示参考实现公开的真实接口。

### 区块 7：睦总结

人物：若叶睦，温和说明。

睦：

> “我准备停下来时，运行时才请守门人检查。”
>
> “如果还有事情没完成，守门人会告诉我缺少什么，让我继续。”

### 本页结论

> Stop Hook 把“模型准备结束”变成一个可验收的候选终态：允许才真正结束，阻止则带着原因回到循环。

### 诚实边界

- Stop Hook 是 Claude Code 运行时提供的可配置生命周期机制，不是 Anthropic Messages API 的 `stop_reason`；
- `stop_hook_blocking` 是参考资料对内部续跑分支的命名，不是公开 Hook 输出字段；
- Stop Hook 可以是命令、HTTP、prompt 或 agent 等不同类型，不能笼统声称它一定由 LLM 判断；
- 页面只解释主 Agent 的 Stop Hook，不展开 `SubagentStop`、`TeammateIdle` 或 `TaskCompleted`；
- Hook 的检查质量决定验收质量，配置了 Hook 不代表任务必然被正确验证。

### 本页不展开

- 不讲 Hook 配置文件的完整语法；
- 不比较退出码阻止与结构化 JSON 输出的全部差异；
- 不实现 prompt/agent 型 Hook 的评估提示词；
- 不展开连续阻止上限的具体产品配置。

### 与下一页的衔接

第 9 页解决了“准备结束以后为什么还可能继续”。下一页进一步解释：即使内层遇到可恢复错误，也不会立刻把错误显示给用户，而是先尝试恢复，只有失败后才向外暴露。

## 附录第 10 页：一次失败，不等于最终失败

### 本页目标

解释生产级 Agent Loop 为什么会暂时扣住可恢复的异常或未完成状态，在内层先尝试恢复，只有恢复失败后才向外暴露最终错误。

关键认知：一次尝试失败，不等于整个查询已经失败。对外暴露的应是最终任务状态，而不是每一次内部尝试的状态。

### 区块 1：墨观察到奇怪的界面状态

人物：若叶墨，盯着终端追问。

墨：

> “刚才那次请求不是失败了吗？”
>
> “为什么界面没有亮红灯，过一会儿却又成功了？”

睦：

> “因为失败的是一次尝试，不是整项任务。”

### 区块 2：两种界面时间线

#### 错误做法：每次尝试失败都立刻上报

```text
请求失败 → UI 显示 failed → 内层恢复、重试 → UI 又变 success
             ↑
       红色终态报错闪了一下
```

任务后来明明恢复成功，用户却先看到了一个虚假的“最终失败”。

#### 正确做法：内层先恢复，外层等待终态

```text
外层 UI：working ─────────────────────────→ success
                   内层第一次失败
                          ↓
                     自动恢复、重试
```

真正恢复失败时：

```text
外层 UI：working ─────────────────────────→ failed
                   内层恢复次数耗尽
```

### 区块 3：恢复闸门

主动取消直接进入 `abort`，已经完整的结果直接进入 `done`；工具自身失败通常构造成带错误标记的 `tool_result` 交给模型修正。下面的闸门只判断其余“异常或未完成状态”是否能够自动恢复。

```text
内层得到异常或未完成状态
            ↓
是否存在明确的恢复策略？
    ├─ 否 → 立即向外暴露
    └─ 是
         ↓
    恢复次数或预算是否仍有剩余？
    ├─ 是 → 暂不发送终态错误
    │        记录诊断 → 准备恢复 → 重新尝试
    │        ├─ 成功 → 正常完成
    │        └─ 失败 → 再次判断
    └─ 否 → 向外暴露最终错误
```

一个状态能够进入自动恢复路径，至少应当同时满足：

1. **已识别**：系统知道遇到的是什么状态；
2. **有动作**：存在与它对应的恢复办法；
3. **有边界**：恢复次数或资源预算存在明确上限。

### 区块 4：前几页中的两个例子

#### `prompt_too_long`

- 先应用已识别、但尚未应用的折叠操作；
- 仍然过长时再执行全量摘要；
- 两条恢复路径都失败后，才向外报告最终错误。

#### `max_tokens`

- 先提高输出上限；
- 仍然不完整时再有限次数续写；
- 继续无法完成时，才把“不完整”转成最终失败。

### 区块 5：教学伪代码

```ts
for (;;) {
  const outcome = await runAttempt();
  if (outcome.cancelled) return abort();
  if (outcome.complete) return outcome;

  const recovery = classifyRecovery(outcome);

  if (recovery.available && recovery.attemptsRemain) {
    rememberDiagnostic(outcome);
    await prepareRetry(recovery);
    continue; // 暂不向外发送“最终失败”
  }

  throw toFinalError(outcome);
}
```

`rememberDiagnostic`、`classifyRecovery` 等名称只表达教学语义，不表示参考实现公开的真实接口。

这里使用 `complete` 而不是 API 请求是否成功：例如 `max_tokens` 可以是一个有效响应，但内容仍未完整，因此还不能进入 `done`。工具失败产生错误 `tool_result` 的流程不在这段伪代码中。

### 区块 6：睦总结

人物：若叶睦，安静说明。

睦：

> “只要还有可靠的办法，我会先在循环里面修复。”
>
> “等所有办法都用尽，才把真正的失败交给外面。”

### 本页结论

> 内层可以知道某次尝试出了问题；外层只有在任务进入最终失败状态后，才需要收到失败事件。

### 诚实边界

- “扣留”描述的是错误传播策略，不代表真实源码一定存在 `heldError` 或 `pendingError` 字段；
- “暂不向外暴露”不等于不记录：日志、计数与诊断信息仍然可以保留；
- 流式文本可能已经展示，因此“用户无感”更准确地说是“用户不会收到虚假的终态报错”；
- `prompt_too_long` 可以表现为请求错误，而 `max_tokens` 是成功响应中的停止原因，所以本页统一称为“异常或未完成状态”；
- 用户主动取消不应被自动恢复；无法通过重试解决的配置、认证或请求错误也不能盲目重试；
- 工具自身失败通常通过带错误标记的 `tool_result` 返回给模型修正，属于另一条处理路径。

### 本页不展开

- 不列出全部网络重试条件；
- 不设计最终错误对象的字段结构；
- 不讨论日志与用户提示的不同脱敏级别；
- 不展开工具失败后的模型自我修正。

### 与下一页的衔接

前几页解决了生产级循环如何稳定地继续和恢复。下一页转向性能：流式响应还没有完全结束时，只要某个工具的参数已经完整，运行时就可以提前开始执行，不必浪费后续等待时间。

## 附录第 11 页：流还没结束，工具已经开跑

### 本页目标

解释 `StreamingToolExecutor` 如何在整个模型响应结束以前，提前启动已经完整、有效且安全的工具调用，并说明这种优化真正节省的是哪一段等待时间。

关键认知：提前执行不会让模型或工具本身变快；它把工具执行时间与模型仍在生成后续内容的时间重叠起来。

### 区块 1：墨发现时间顺序不对

人物：若叶墨，看着仍在滚动的终端。

墨：

> “模型明明还在输出后面的内容……”
>
> “为什么第一个文件已经读完了？”

### 区块 2：一个工具块怎样变得可用

下面以 Anthropic 的块级流式事件为例；这些事件名不是所有模型提供商共用的协议。

工具参数不是一次性到达，而是随着流式事件逐段传输。

```text
content_block_start
  得到 tool_use 的 index、id 与 name
            ↓
input_json_delta
  按 index 累积 partial_json
            ↓
content_block_stop
  当前工具块在协议层关闭
            ↓
解析 JSON，并执行 Schema 与业务验证
```

`content_block_stop` 是块级结束事件，不表示整条模型响应已经结束。第一个工具块关闭以后，后面的文本或其他工具块仍可能继续传输。

同时，工具块关闭也不保证输入一定有效：如果 JSON 被截断、无法解析或输入验证失败，它就不能进入提前执行。

### 区块 3：串行等待与提前执行

#### 串行方式

```text
[=========== API 流式响应 ===========][tool 1][tool 2]
```

整个响应结束后，才开始执行所有工具。

#### 提前执行

```text
[=========== API 流式响应 ===========]
          └─ tool 1 已完整 → [tool 1]
                       └─ tool 2 已完整 → [tool 2]
```

第一个工具块准备好以后，它的执行时间可以与剩余响应流重叠；多个彼此安全的工具也可以相互重叠。

能够隐藏的等待时间大致受两者中的较小值限制：

```text
min(工具执行耗时, 工具块完成后的剩余流式时间)
```

工具块越靠前、后续响应越长、工具越适合并发，收益通常越明显。它不减少模型生成的 Token、API 成本或工具自身耗时。

### 区块 4：提前执行的四道闸门

只有同时通过以下检查，工具才可以提前启动：

1. **Block 已关闭**：收到当前工具块的块级结束事件；
2. **输入有效**：JSON 解析、Schema 与业务逻辑验证通过；
3. **并发安全**：该工具及本次输入允许与剩余工作重叠，通常是无副作用的只读调用；
4. **权限已允许**：权限系统已经返回允许，不需要等待用户确认。

写文件、执行命令、存在顺序依赖或需要用户确认的工具不能为了速度跳过这些约束。

### 区块 5：教学伪代码

```ts
const earlyExecutions = new Map<string, Promise<ToolResult>>();

onToolBlockComplete(block => {
  if (
    validateInput(block) &&
    isConcurrencySafe(block.name, block.input) &&
    checkPermission(block) === "allow"
  ) {
    earlyExecutions.set(block.id, executeTool(block));
  }
});

// 当前模型响应结束后，仍然进入正常工具处理流程。
const result = earlyExecutions.has(toolUse.id)
  ? await earlyExecutions.get(toolUse.id) // 复用已经启动的任务
  : await executeTool(toolUse);           // 此时才执行
```

使用 `tool_use.id` 保存 Promise 或 Task，可以让正常工具处理流程复用提前执行的任务，避免同一个工具被执行两次。

### 区块 6：协议没有改变

提前执行只移动了工具真正开始工作的时间，没有改变 Agent Loop 的消息协议。

```text
当前 assistant 响应仍需结束
            ↓
运行时收集或等待工具结果
            ↓
下一轮把 tool_result 交还模型
```

工具结果不能插回仍在生成的同一个 assistant 响应。

### 区块 7：睦总结

人物：若叶睦，安静说明。

睦：

> “工具并没有跑得更快。”
>
> “我们只是没有等我把整段响应说完，才开始做已经确定的事情。”

### 本页结论

> 流式工具执行的收益来自时间重叠：模型继续生成时，已经完成且安全的工具调用并发执行。

### 诚实边界

- 生产实现应默认禁止提前并发，只对已经确认安全的工具与输入开放；
- 教学实现可以用只读工具集合简化判断，但真实并发安全性可能还与具体输入有关；
- 权限检查、输入验证、并发上限和顺序屏障仍然有效；
- 如果响应后来失败或被取消，提前任务应能够取消，或保证其结果可以安全丢弃；
- 参考资料中的流式窗口与加速倍数属于经验示例，不是性能保证；
- 客户端的 `StreamingToolExecutor` 与 API 提供的服务端工具不是同一种机制。

### 本页不展开

- 不实现流式 JSON 事件解析器；
- 不设计完整的并发调度器；
- 不处理跨工具的读写依赖图；
- 不比较所有模型提供商的流式协议。

## 附录第 12 页：最后，把它装回一张图

### 本页目标

用一张总览图把前十一页重新组合为同一个生产级 Agent Loop，帮助读者区分主循环、运行时分支和旁路优化。

关键认知：前十一页不是十一套系统，而是同一个循环在不同边界下作出的继续、恢复与停止决策。

### 区块 1：墨终于把所有概念连起来

人物：若叶墨，恍然大悟。

墨：

> “原来这些不是十一套系统……”
>
> “只是同一个循环，在不同边界下决定怎么继续？”

### 区块 2：最外层——`QueryEngine`

```text
接收用户输入
      ↓
恢复并管理会话状态
      ↓
for await 消费 queryLoop 产生的事件
      ↓
统计、保存与输出最终状态
      ↓
等待下一次用户输入
```

`QueryEngine` 管理整段会话的生命周期，包括用户输入、预算与 Token 统计、会话恢复和保存。API 调用、工具执行与恢复细节仍属于内层 `queryLoop`。

`queryLoop` 使用 `yield` 产生事件，外层使用 `for await` 逐个消费；两端的握手形成背压。

### 区块 3：最内层——`queryLoop` 的三步主干

```text
① 由完整历史构造本轮 API 视图
                 ↓
② 流式调用模型
   得到 content + stop_reason，或请求错误
                 ↓
③ 运行时分类
   完成？行动？恢复？继续？
```

无论生产实现增加多少分支，主干仍然是构造请求、调用模型、判断下一步。

### 区块 4：流式工具执行是一辆“侧车”

`StreamingToolExecutor` 发生在第 ② 步仍在进行时：

```text
完整 tool_use block
      ↓
JSON 与输入验证通过
      ↓
并发安全且权限允许
      ↓
按 tool_use.id 保存提前执行的 Promise / Task
```

当前响应结束后，正常工具处理流程再复用任务并收集 `tool_result`。

它优化的是工具何时启动，不是新的 `stop_reason`，也不是第八种 continuation reason。

### 区块 5：运行时分类下的七种续跑原因

#### 正常行动

```text
next_turn
```

执行或复用工具，收集 `tool_result`，写入下一轮消息。

#### 上下文恢复

```text
collapse_drain_retry
reactive_compact_retry
```

先应用轻量折叠，不够时再执行更重的全量摘要。

#### 输出恢复

```text
max_output_tokens_escalate
max_output_tokens_recovery
```

先提高输出上限，不够时再有限次数续写。

#### 系统要求

```text
stop_hook_blocking
token_budget_continuation
```

停止条件尚未满足，或参考实现内部判断仍需继续时，准备下一轮状态并回到循环入口。

`token_budget_continuation` 只作为参考项目的内部分类展示，不与公开 API 的某个 `stop_reason` 建立未经证实的一一映射。

### 区块 6：恢复闸门决定错误何时向外传播

```text
状态已识别 + 存在恢复动作 + 次数或预算仍有剩余
                         ↓
                   留在 queryLoop
                         ↓
              准备恢复并回到循环入口

未知状态，或恢复次数与预算已经耗尽
                         ↓
                    final error
                         ↓
                    QueryEngine
```

恢复闸门决定传播时机，不是新的续跑原因。

### 区块 7：三种终态出口

#### 正常完成：`done`

只有在以下条件同时成立时，当前查询才正常完成：

- 没有工具或其他续跑原因；
- 自动恢复路径不再要求重试；
- Stop Hook 允许停止。

#### 主动取消：`abort`

用户发出取消信号以后：

- 取消信号传给仍在进行的 API 请求与相关任务；
- 循环在取消检查点退出；
- 运行时执行必要的清理与保存。

主动取消不是 continuation reason，也不应被自动恢复逻辑重新拉起。

#### 最终失败：`final error`

遇到未知状态，或明确恢复路径的次数与预算已经耗尽时，内层把最终错误交给外层。

无论以哪种终态结束，`queryLoop` 都把最终状态交给 `QueryEngine`，由外层完成统计、保存与后续会话管理。

### 区块 8：教学伪代码

```ts
async function* queryLoop(state) {
  for (;;) {
    state.signal.throwIfAborted();
    const request = buildApiView(state);
    const outcome = yield* streamModelEvents(request, {
      signal: state.signal,
      onSafeToolReady: startSafeToolsEarly,
    });
    const decision = await classify(outcome, state);

    if (decision.kind === "continue") {
      await decision.prepare();
      continue; // 每条恢复路径都回到同一个循环入口
    }

    if (decision.kind === "done") return;
    throw decision.finalError;
  }
}
```

`streamModelEvents` 是教学用的异步生成器名称：它逐个产出可观察事件，并在结束时返回最终 `outcome`；`yield*` 把这些事件继续交给外层 `QueryEngine`，因此外层 `for await` 的消费速度能够形成背压。真实实现需要保留更细的事件、状态与恢复计数。

### 区块 9：睦收束本章附录

人物：若叶睦，安静总结。

睦：

> “这些续跑分支走的是不同岔路，最后都会带着新的状态，回到同一个循环入口。”
>
> “工程系统只是决定何时继续、怎样恢复，以及什么时候真正停下。”

### 本页结论

> 生产级 Agent Loop 仍然是“请求 → 模型 → 行动 → 结果 → 决定是否继续”；复杂性来自它对边界情况的负责。

### 诚实边界

- 总览图只表达职责与控制流，不对应真实源码的逐行调用关系；
- `stop_reason` 是 API 返回的事实，七种 continuation reason 是运行时决策，两者不是同一枚举；
- `StreamingToolExecutor` 是发生在流式调用期间的时间优化，不能画成响应结束后的续跑分支；
- 恢复闸门决定错误何时向外传播，不应被算作第八种续跑原因；
- 用户主动取消是独立的终态出口，不是错误恢复分支；
- 工具提前执行不代表可以在当前 assistant 响应结束前回传 `tool_result`。
