## read_file
```ts
type ToolDef = {
  name: string;
  description: string;
  input_schema: {
    type: "object";
    properties: Record<string, unknown>;
    required: string[];
  };
};

// src/tools/read-file.ts
export const readFileTool: ToolDef = {
  name: "read_file",
  description: "Read the contents of a file. Returns the file content with line numbers.",
  input_schema: {
    type: "object",
    properties: {
      file_path: { type: "string", description: "The path to the file to read" },
    },
    required: ["file_path"],
  },
};

// src/tools/index.ts
export const toolDefinitions = [readFileTool];
```

```ts
export function readFile(input: { file_path: string }): string {
  try {
    const content = readFileSync(input.file_path, "utf-8");
    return content
      .split("\n")
      .map((line, index) => `${String(index + 1).padStart(4)} | ${line}`)
      .join("\n");
  } catch (error) {
    return `Error reading file: ${error instanceof Error ? error.message : String(error)}`;
  }
}
```
核心思路：
1. 读取文件
2. 分行
3. 补充行号
4. 拼接返回
5. 异常兜底

为了保证稳定性，这里补充了单元测试，跑命令：`pnpm test` 即可验证

## write_file
> 从这部分开始不再重复说明 ToolDef 类型；每个工具仍建议补充对应单元测试。

```ts
function writeFile(input: { file_path: string; content: string }): string {
  try {
    const dir = dirname(input.file_path);
    if (!existsSync(dir)) mkdirSync(dir, { recursive: true });
    writeFileSync(input.file_path, input.content);
    return `Successfully wrote to ${input.file_path}`;
  } catch (e) {
    return `Error writing file: ${e instanceof Error ? e.message : String(e)}`;
  }
}
```

核心思路：
1. 获取文件的目录
2. 如果父目录不存在，则创建
3. 将输入内容写入到文件
4. 输出写入成功的信息
5. 异常兜底

## edit_file
```ts
function editFile(input: { file_path: string; old_string: string; new_string: string }): string {
  try {
    if (input.old_string.length === 0) {
      return "Error: old_string must not be empty.";
    }
    const content = readFileSync(input.file_path, "utf-8");
    const count = content.split(input.old_string).length - 1;
    if (count === 0) {
      return `Error: old_string not found in ${input.file_path}`;
    }
    if (count > 1) {
      return `Error: old_string found ${count} times in ${input.file_path}. Must be unique.`;
    }
    // split().join() 比 replace() 更安全一点，因为它不会触发 $ 替换语义
    const updated = content.split(input.old_string).join(input.new_string);
    writeFileSync(input.file_path, updated);
    return `Successfully edited ${input.file_path}`;
  } catch (e) {
    return `Error editing file: ${e instanceof Error ? e.message : String(e)}`;
  }
}
```
1. 如果 old_string 为空，直接返回错误
2. 读取指定文件的内容 content
3. content 如果不包含旧字符串，则报错没有找到
4. 如果出现多次，要求模型提供更多上下文来标识唯一修改点（宁失败也不猜测，静默匹配第一个要比告知失败危险的多）
5. 在确认旧字符串只出现一次后，将它替换为新字符串
6. 更新写入文件
7. 提示成功信息
8. 兜底报错

### 引号容错 + Diff 输出
基础版本只能做精确字符串匹配，但 LLM 有时会把直引号和弯引号混用，例如文件里是 `const msg = “hello”`，模型传入的是 `const msg = "hello"`。

所以先做引号标准化匹配，但真正替换时仍然使用文件中的原始字符串。

```ts
function normalizeQuotes(value: string): string {
  return value
    .replace(/[\u2018\u2019\u2032]/g, "'")
    .replace(/[\u201C\u201D\u2033]/g, '"');
}

function findActualString(fileContent: string, searchString: string): string | null {
  if (fileContent.includes(searchString)) return searchString;

  const normalizedFile = normalizeQuotes(fileContent);
  const normalizedSearch = normalizeQuotes(searchString);
  const index = normalizedFile.indexOf(normalizedSearch);

  if (index === -1) return null;
  return fileContent.slice(index, index + searchString.length);
}
```

注意：唯一性检查也要基于标准化后的字符串；如果标准化后出现多次，仍然要拒绝编辑，避免猜测修改位置。

另外再添加一个方法，用于在编辑成功后返回简易 diff，方便确认修改点：

```ts
function generateDiff(content: string, oldString: string, newString: string): string {
  const lineNumber = content.slice(0, content.indexOf(oldString)).split("\n").length;

  return [
    `@@ -${lineNumber},1 +${lineNumber},1 @@`,
    `- ${oldString}`,
    `+ ${newString}`,
  ].join("\n");
}
```

以上 3 个方法会在 `edit_file` 中使用，具体整合逻辑参见源码，这里不再展开。

## list_files

```ts
async function listFiles(input: { pattern: string; path?: string }): Promise<string> {
  try {
    const files = await glob(input.pattern, {
      cwd: input.path || process.cwd(),
      nodir: true,
      ignore: ["node_modules/**", ".git/**"],
    });

    if (files.length === 0) {
      return "No files found matching the pattern.";
    }

    return files.slice(0, 200).join("\n");
  } catch (e) {
    return `Error listing files: ${e instanceof Error ? e.message : String(e)}`;
  }
}
```

核心思路：
1. 使用 glob pattern 根据参数匹配文件
    1. `pattern` 必填，用来描述要匹配的文件，例如 `*.ts`、`**/*.ts`、`src/**/*`
    2. `path` 可选，用来指定搜索基准目录，默认是当前工作目录
    3. 是否递归由 `pattern` 决定，不在工具里固定递归
    4. 只返回文件，不返回目录
    5. 忽略 `node_modules/**` 和 `.git/**`
2. 最多返回前 200 条，避免结果过长
3. 没有匹配文件时，返回空结果提示
4. 异常兜底

## grep_search
`grep_search` 用来在文件内容里搜索正则匹配项，返回包含文件路径、行号和匹配行的结果。

它适合回答“哪里定义了某个函数”“哪些文件引用了某个变量”这类问题。

```ts
function grepSearch(input: { pattern: string; path?: string; include?: string }): string {
  try {
    const args = ["--line-number", "--color=never"];
    if (input.include) args.push("-g", input.include);
    args.push("--", input.pattern);
    args.push(input.path || ".");

    const result = execFileSync("rg", args, {
      encoding: "utf-8",
      maxBuffer: 10 * 1024 * 1024,
      timeout: 10000,
    });

    const lines = result.split("\n").filter(Boolean);
    return lines.slice(0, 100).join("\n") +
      (lines.length > 100 ? `\n... and ${lines.length - 100} more matches` : "");
  } catch (e) {
    if (e.status === 1) return "No matches found.";
    if (e.code === "ENOENT") return "Error: ripgrep (rg) is not installed.";
    if (e.code === "ENOBUFS") {
      return "Error: too many matches to buffer; narrow the pattern, path, or include filter.";
    }
    return `Error: ${e instanceof Error ? e.message : String(e)}`;
  }
}
```

核心思路：
1. 处理参数，参数说明：
    1. `pattern` 必填，表示要搜索的正则
    2. `path` 可选，表示搜索路径，默认是当前目录
    3. `include` 可选，用来限制文件类型，例如 `*.ts`
2. 使用 `rg --line-number` 搜索并返回行号
3. 最多返回前 100 条，避免结果过长
4. 异常兜底
    1. `rg` 退出码为 1 表示没有匹配，不算异常
    2. 如果没有安装 `rg`，返回明确错误
    3. 如果匹配结果过大导致 buffer 溢出，提示缩小搜索范围
    4. 默认兜底

为什么这里cc使用的是 `rg`（ripgrep）， 而不是系统 `grep`？原因是 `rg` 更适合代码搜索：
- 默认递归
- 默认尊重 .gitignore
- 默认跳过隐藏目录、二进制文件、node_modules 这类常见噪音更少
- 速度通常比 grep -r 快很多
- 输出格式天然适合代码搜索：path:line:match
- 跨平台体验更好

系统 `grep` 虽然更基础、通常自带，但需要额外处理递归、忽略目录和不同平台参数差异。

## run_shell
```ts
function runShell(input: { command: string; timeout?: number }): string {
  try {
    const result = execSync(input.command, {
      encoding: "utf-8",
      maxBuffer: 5 * 1024 * 1024,
      timeout: input.timeout || 30000,
      stdio: ["pipe", "pipe", "pipe"],
      shell: process.platform === "win32" ? "powershell.exe" : "/bin/sh",
    });

    return result || "(no output)";
  } catch (e: any) {
    const stderr = e.stderr ? `\nStderr: ${e.stderr}` : "";
    const stdout = e.stdout ? `\nStdout: ${e.stdout}` : "";
    if (e.code === "ETIMEDOUT" || (e.signal === "SIGTERM" && e.status === null)) {
      return `Command timed out after ${input.timeout || 30000}ms${stdout}${stderr}`;
    }
    if (typeof e.status === "number") {
      return `Command failed (exit code ${e.status})${stdout}${stderr}`;
    }
    return `Error: ${e instanceof Error ? e.message : String(e)}`;
  }
}
```

核心思路：
1. 处理参数，参数说明：
    1. `command` 必填，表示要执行的 Shell 命令
    2. `timeout` 可选，单位是毫秒，默认 `30000`
2. `execSync` 执行
    1. 使用 Shell 执行命令；成功时返回 stdout，失败时从异常对象里取 stdout 和 stderr
    2. 使用 `maxBuffer` 限制输出大小，避免命令输出过大撑爆进程
3. 输出命令结果，如果没有内容则返回 `(no output)`
4. 异常兜底
    1. 命令失败时，同时返回 exit code、stdout 和 stderr
    2. 命令超时时，返回明确的 timeout 信息
    3. 默认兜底

注意：这个工具的能力边界比前几个工具大很多，因为它可以执行任意命令。

我们做了 timeout 和 maxBuffer 的处理，危险命令确认、权限规则、plan mode 禁止 shell 等安全逻辑放在后续权限系统里处理。

## 工具结果截断
工具执行结果最终会进入消息数组，继续发回给模型。结果太长会占用大量上下文，甚至影响后续模型调用。

因此可以在工具分发层统一做一次结果截断，而不是让每个工具都重复处理。

```ts
const MAX_RESULT_CHARS = 50000;

function truncateResult(result: string): string {
  if (result.length <= MAX_RESULT_CHARS) return result;

  const keepEach = Math.floor((MAX_RESULT_CHARS - 60) / 2);
  return (
    result.slice(0, keepEach) +
    `\n\n[... truncated ${result.length - keepEach * 2} chars ...]\n\n` +
    result.slice(-keepEach)
  );
}
```

核心思路：
1. 设置统一的工具结果长度上限
2. 未超过上限时直接返回
3. 超过上限时保留头部和尾部
4. 中间插入明确的截断提示，告诉模型有多少字符被省略
5. 在 `executeTool` 里统一调用，让所有工具都受保护

为什么保留头尾，而不是只保留开头？因为很多命令的关键结果在末尾，例如编译错误摘要、测试失败统计、最终 exit 信息等。

注意：这和 `grep_search` 自身最多返回前 100 条不冲突。`grep_search` 的限制是工具内部的业务截断；这里是工具结果进入消息数组前的统一兜底。
